# Uniscope — Project Context for Claude Code

Mentorship marketplace connecting prospective medical students (Aspirants) with verified mentors (current students/alumni) for chat and paid audio-call guidance, plus honest college reviews.

**Branch:** `feature/flutter-migration` (mobile was ported from React Native to Flutter mid-project; backend/admin unaffected).

## Stack

| Layer | Tech |
|---|---|
| Mobile | Flutter (`mobile_flutter/`) — Riverpod, go_router, Dio |
| Backend | NestJS + TypeScript (`backend/`) — Prisma 7 ORM |
| Database | PostgreSQL on Supabase (pooler connection; `DIRECT_URL` bypasses pooler for migrations) |
| Admin panel | Next.js (`admin/`) — single hardcoded admin login, kept as a **separately-deployed, non-public** surface (not linked from user-facing app) |
| Auth | Phone OTP (Twilio Verify, or `mock` provider for local dev) + JWT access/refresh |
| Real-time chat | Postgres (persistence, via Prisma) + Supabase Realtime Broadcast (content-free "new message" ping — see "Chat architecture" below). Replaced Stream Chat (cost-driven migration, 2026-09-02). |
| Audio calls | **Live in production: Agora.** Client has since decided to move to **Stream Video** (not LiveKit — that path was built, briefly auto-deployed by accident, then reverted; see "Calls migration status" below) — fully built and live-tested against the real Stream account on `migration/agora-to-stream-calls`, not yet merged, blocked only on real-device testing (see below). |
| Payments | Razorpay (Orders API + webhook, also a direct client-confirm fallback for local dev since webhooks need a public URL) |

Root is an npm workspace monorepo (`backend`, `admin`; `mobile_flutter` is separate/Flutter, not an npm workspace member).

## Local dev setup

- Backend: `cd backend && npm run start:dev` (or build+run `dist/main.js` directly — see below). Runs on port **3001**, prefix `/api/v1`.
- Admin: `npm run dev --workspace=admin` — **must use `next dev --webpack`**, not the Turbopack default (Turbopack can't resolve `lightningcss`'s native binding in this monorepo's hoisted `node_modules`; already fixed in `admin/package.json`).
- Mobile: `flutter run --dart-define=API_URL=http://10.0.2.2:3001/api/v1` for Android emulator (localhost aliasing), or your LAN IP for a physical device.
- All secrets live in `backend/.env` and `admin/.env.local` (both gitignored). See `backend/.env.example` for the full list — Supabase, Twilio, Redis (Upstash), Razorpay, Agora, JWT secrets are all already populated in the working `.env` for this project's own accounts. (No separate chat-vendor secret — chat reuses the same Supabase project/keys already configured for storage.)
- Admin login (local dev): credentials are in `admin/.env.local` (`ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_SESSION_SECRET`) — not committed.
- **Mobile login in `mock` OTP mode**: any phone number, code is always the fixed `MOCK_OTP_FIXED_CODE` in `backend/src/auth/otp/mock-otp.provider.ts` (currently `111111`) — deliberately not random, so anyone can log in without reading server logs. Only applies when `OTP_PROVIDER_TYPE=mock`; switching to `twilio` sends and requires a real SMS code again. Don't ship this backend reachable outside localhost while in mock mode — the fixed code means anyone who can reach it can log in as any phone number.
- **A recurring dev-server gotcha:** the Supabase free-tier project auto-pauses after inactivity; if DB calls start failing, check the Supabase dashboard shows the project "Active" and retry.
- **Backend restart pattern used throughout this project's history** (Claude_Preview MCP tools were unreliable mid-session): `rm -f tsconfig.build.tsbuildinfo && npx tsc -p tsconfig.build.json && node dist/main.js` backgrounded, health-check via `curl localhost:3001/health`.

## Prisma workflow (Prisma 7 — syntax changed from earlier versions)

- No `url` in `datasource db` block — reads `DATABASE_URL`/`DIRECT_URL` from `prisma.config.ts`.
- Generate a migration from a schema diff (works against the live dev DB, non-interactive-safe):
  ```
  npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
  ```
  Then hand-create the migration folder (`prisma/migrations/<YYYYMMDDHHMMSS>_<name>/migration.sql`, 14-digit timestamp prefix required) and `npx prisma migrate deploy`.
- For **enum value remaps** (not just additions), Prisma's diff tool can't express the data transformation — hand-write the migration using the create-new-type / `ALTER TABLE ... USING (CASE ...)` / drop-old-type / rename pattern. See `prisma/migrations/20260712125549_collapse_user_role_to_aspirant_mentor/migration.sql` for a worked example (this preserved existing user data instead of resetting).
- `prisma migrate dev` and `migrate reset` require a TTY — don't work in a non-interactive agent session. Use `migrate diff` + `migrate deploy` instead.

## Business model decisions (locked in, don't re-litigate without asking)

- **Roles:** collapsed to `ASPIRANT` / `MENTOR` / `ADMIN` (previously 4 granular roles — migrated, not reset).
- **Mentors are no longer medical-only — Uniscope expanded to all academic streams (Medical, Dental, Engineering, Arts & Humanities, Commerce & Business, Law, Design, Others).** This reverses the earlier "medical/dental alumni only" rule. `UserProfile.stream` (mentor-role usage — dual-purpose with the aspirant's school-level PCB/PCM stream, same pattern as `specialty`) is now the primary discovery/filter attribute (`kMentorStreams` in `profile_options.dart`); the old Areas-of-Guidance wizard step and its `specialty` picklist (`kGuidanceAreas`) were removed from the mentor onboarding wizard but the field/const still exists for backward compatibility with mentors who set it before this change, and is still used by `EditProfileScreen` (not yet updated for the multi-stream reality — worth revisiting). Mentor cards/detail screens now show `stream` when `specialty` is unset.
- **Mentor onboarding wizard collects a real name + self-chosen alias up front**, rather than relying on the auto-generated pseudonym. `UserProfile.realNameEncrypted` (AES-256-GCM, `PROFILE_ENCRYPTION_KEY` env var, `src/common/helpers/profile-encryption.helper.ts`) stores the real name — never returned in any response projection, write-only via `UpdateProfileDto.realName`. The alias *is* `User.displayName`, checked live for availability via `GET /users/check-display-name` (case-insensitive lookup, not a DB-level unique constraint — no existing collisions found when this was added). Mentor wizard structure, in order: Basic Information (full name, alias, DOB, gender) → Location (state, city) → College Details (college, stream, degree) → Current Status (studying/graduated + year, using the already-existing `UserProfile.yearOfStudy`/`graduationYear` columns) → identity verification (college ID upload, unchanged). "Skip for now" only appears on the final (verification) step — the other four are mandatory. The wizard is reached directly from Role Selection (mentors skip the shared `ProfileSetupScreen` entirely, since Basic Information covers the same ground) and ends by going straight to Home.
- **Currency:** "Uniminutes" wallet. Internally still paise-denominated (`Wallet.balanceMinor`, `LedgerEntry.amountMinor` — architecture principle: money is always integer minor units, never floats), but 1 Uniminute = 1000 minor units = ₹10, matching the **flat mentor call payout rate** (all mentors currently earn the same ₹10/min for calls — this was a late-session decision that supersedes an earlier "per-mentor custom rate" discussion; worth double-checking with the user if extending this).
- **Recharge margin:** min ₹250 recharge credits 20 Uniminutes (₹200 of spendable value) — the 20% margin is baked into the recharge conversion only, **never** shown to the user as a line item, and **never** taken again at session-billing time (mentor gets paid the exact same amount debited from the aspirant). See `WalletService.computeTopupCredit`.
- **Uniminutes are the only student-facing unit. Rupees appear at wallet top-up and nowhere else.** 1 Uniminute = 1 minute of call time = 1000 minor units, so a balance reads directly as "minutes I can talk". Call cost is never expressed in ₹ on any aspirant surface (mentor cards, mentor profile, slot picker, in-call, session list, ledger) — only the top-up sheet shows ₹, because that's the only moment real money changes hands. Mentor-side surfaces (earnings, payouts) stay in ₹ since mentors withdraw to a real bank account. Helpers: `minorToUniminutes` / `slotUniminutes` / `uniminutesLabel` in `mobile_flutter/lib/core/network/wallet_api.dart`.
- **Never advertise that chat is free.** Chat being free is the baseline assumption, not a feature to sell — no "Free chat" chips, no "Chat · Free" buttons, no "chatting is always free" footnotes. The Chat button just says "Chat". (This reverses earlier copy that labelled chat as free in several places.)
- **Mentor availability is stated intent, NOT real-time presence — and the app must never imply otherwise.** `UserProfile.isMentorAvailable` is the mentor's own "Accepting call bookings" switch. It gates **only** AUDIO_CALL booking; it never hides a mentor from discovery (they stay listed and chat-reachable either way), and it says nothing about whether their app is open. Real presence was **deliberately not built**: a call is already asynchronous (request → mentor accepts → connect later), mentors are medical students who'd read as offline most of the day, and a green "online" dot the app can't back becomes a refund ticket when a paid call no-shows. Consequences to preserve: (1) never label this "online"/"offline" — the UI says "Accepting calls" / "Chat only", and the shared widget is `CallAvailabilityChip`, deliberately not a bare status dot; (2) availability **auto-expires after 24h** (`AVAILABILITY_TTL_HOURS`, `availabilitySetAt`) so a forgotten toggle can't advertise a stale promise; (3) every read path — mentor list, mentor detail, the booking gate, and the mentor's *own* profile switch — must go through `isCallAvailable()` in `modules/mentors/availability.ts`, because if the mentor and the student disagree about bookability that's a support ticket. (Historical note: this used to also flag that Stream Chat's "last seen" was a separate signal from the chat vendor — no longer applicable now that chat has its own Postgres+Realtime backend with no presence feature at all, see "Chat architecture" below.) If the product ever moves to on-demand/instant calls, revisit — that's the case where real presence starts earning its cost.
- **Audio call billing:** fixed pre-paid slots only — 6/10/20 min (`CreateSessionDto.CALL_SLOT_MINUTES`; shortest slot was 5, changed to 6 2026-09-02 per explicit client request — the no-show grace period and overrun extension both derive from this constant, so both followed automatically, no separate change needed), not live per-minute metering. Student picks a slot at booking; balance is checked and a `WalletHold` placed **at booking time**, before the mentor ever sees the request.
- **Free tier:** 2 free chat sessions + 10 free call minutes per aspirant (`UserProfile.freeChatsRemaining` / `freeCallSecondsRemaining`).
- **Call connect confirmation:** billing only fires once **both** the aspirant's and mentor's clients independently report "I joined" (`POST /sessions/:id/call/joined`) — an interim fraud-resistance measure until a real Agora server-side "user joined channel" webhook is configured (needs additional Agora Console setup the user hasn't done yet). Neither party alone can trigger a charge.
- **Call overrun:** hard cutoff at slot end, with a "continue?" popup offering another fixed +5 min block (`POST /sessions/:id/call/extend`), billed the same way as the original booking.
- **Call no-show / grace period:** a call still in `ACCEPTED`/`RINGING` (mentor accepted, but the two sides haven't both confirmed "joined" yet) is auto-resolved once **half the booked slot's minutes** have passed since the mentor's accept (`respondedAt`) — 5-min slot → 2.5 min grace, 10-min → 5 min, 20-min → 10 min, always exactly 50%, no special-casing per slot size (money is minor-unit integers throughout, so the fractional 2.5 min on a 5-min slot is still an exact 2500-minor fee, never a rounding problem). `SessionsService.sweepCallNoShows` (`@Interval`, every 30s) does the sweeping; `resolveNoShow` does the actual settling, status → `FAILED`. Money only moves one way: **aspirant no-show** (mentor showed, aspirant didn't) charges the aspirant exactly the grace-period-equivalent fee and credits the mentor the same amount in full (same zero-margin same-amount pattern as every other session billing path) — `endReason: 'ASPIRANT_NO_SHOW'`. A free-tier booking (no `WalletHold`) has no mentor payout to fund on a no-show either, same as a normal free-tier connect — the aspirant's free-call-seconds are decremented by the grace period instead, so it's still not consequence-free for them. **Mentor no-show** (aspirant showed, mentor didn't) and **mutual no-show** (neither showed) both fully release the hold — nobody is charged, mentor gets nothing — `endReason: 'MENTOR_NO_SHOW'` / `'NO_ANSWER'`. Mobile: `SessionListScreen._statusLabel` shows a role-specific label for each (e.g. aspirant sees "No-show — you were charged", mentor on the same session sees "Aspirant no-show — you were paid") instead of a generic "Failed". Verified live against the real DB for both the aspirant-no-show (fee+credit landed correctly) and mentor-no-show (hold released, zero charged) cases.
- **Mentor-side call drop:** still bills the aspirant in full — **never** an automatic refund. The aspirant gets a Report action; an admin manually reviews and can issue a `REFUND` ledger entry via `PATCH /reports/:id/resolve`. See `ReportsService.resolve`.
- **Support chat:** a persistent, session-independent chat channel per user with a fixed "UniScope Support" identity (`SUPPORT_ACCOUNT_ID` in `chat.service.ts`), lazily provisioned via `GET /chat/support/messages`. This is what the "Need Help?" banner in the UI is wired to. No admin-side reply path exists yet — a user can message support, but nothing lets staff reply *as* the sentinel identity (same gap that existed pre-migration).
- **Aspirant Sessions tab shows one row per mentor, not one per session (2026-09-02, explicit product decision).** `session_list_screen.dart`'s `_groupAllSessionsByCounterpart` collapses every chat/call session with the same mentor into one relationship — a long-running mentor relationship no longer reads as a scrolling wall of near-duplicate cards. A currently-actionable session (pending/accepted/ringing/in progress) still gets its own inline action row on that mentor's card; everything else (completed/cancelled/rejected/expired) collapses into a "+N earlier" tap target (`showMentorSessionHistory`) — a sheet listing that mentor's full history, reachable either from that collapsed row or from a history icon inside `SessionChatScreen` itself. **Mentor accounts are deliberately unaffected** — a mentor serves many different students and still needs each one's individual request visible separately (`_groupActiveSessions`, the pre-existing behavior, untouched). Paired with this: `ActiveSessionDock` (the pending-call banner) is no longer global for aspirants — `MainShell` only mounts it for mentor accounts now; an aspirant's own pending-call status shows scoped inline inside that specific mentor's `SessionChatScreen` (`ActiveSessionDock(mentorId: ...)`) instead of floating over every tab regardless of which mentor it's for. Mentors keep the global one, same reasoning as above.

## What's built (backend modules, all tested live against the real Supabase DB + real Razorpay/Agora APIs — not just unit-style tests)

## Chat architecture (migrated off Stream Chat, 2026-09-02 — cost-driven)

Two Prisma models: `ChatChannel` (`SESSION` type, one per CHAT-type `Session`; or `SUPPORT` type, one per user, persistent) and `ChatMessage` (`text`, `senderId`, `channelId`, `clientMessageId` for send-retry idempotency, indexed `(channelId, createdAt)` for pagination). Postgres is the single source of truth for message content — nothing about a message ever leaves through any other channel.

**Realtime delivery is deliberately content-free.** `ChatService.sendMessage` persists the message, then does a best-effort Supabase Realtime **Broadcast** `httpSend('new_message', {})` on topic `chat:<channelId>` — an empty-payload ping, never the text. Mobile subscribes to that topic with the public Supabase anon key and, on any ping (or on first successfully subscribing, or on app-resume), refetches history over the authenticated REST API. This sidesteps needing Postgres RLS / Supabase Realtime Authorization, which would otherwise require handing Supabase a session it can verify — this app has no native Supabase Auth session (custom phone-OTP+JWT), so there's nothing for RLS to key off. **Verified live against the real Supabase project** that this is actually safe: `chat_channels`/`chat_messages` have RLS disabled (like every table in this app), but the `anon`/`authenticated` Postgres roles have zero GRANTs on them either — so even though the anon key ships to every mobile client, Supabase's public REST API (PostgREST) cannot be used to read chat data directly, only the NestJS-authorized path can. This is correct today but fragile: any future Supabase Studio action that grants `anon`/`authenticated` SELECT on a public table (e.g. its table editor's "Enable API access" convenience) would silently expose this data with no RLS to stop it. Re-check grants (`information_schema.role_table_grants`) after any hands-on Supabase Studio session.

**Authorization** (`ChatController.requireChannel`): a session's chat is readable/writable only by its two parties (aspirant/mentor), only while the session is `ACCEPTED`/`IN_PROGRESS`/`COMPLETED` (so history stays readable after a session ends, matching the rest of the app's "never erase access to something already shared" pattern), 404-not-403 for a non-party. **Blocking gates sending, not reading**: if either party has blocked the other, `sendMessage` 403s in both directions, but `listMessages` still works for both — an existing conversation's history doesn't disappear just because someone got blocked later.

**Idempotent sends**: `SendMessageDto.clientMessageId` (a client-generated UUID, unique per `(channelId, clientMessageId)`) — a retried/double-tapped POST with the same id returns the original message instead of creating a duplicate, and skips re-notifying/re-pinging. Mobile's `ChatThreadView` mints one id per logical send attempt and reuses the *same* id on a manual retry (via the "Retry" SnackBar action) — generating a fresh id on retry would defeat the whole point.

**Push + in-app notifications**: `ChatService.sendMessage` notifies whoever didn't just send (both session parties minus the sender, for SESSION channels; the real user, for a SUPPORT-channel reply from the sentinel — moot today since nothing replies as the sentinel yet) via the existing `NotificationsService` (`NotificationType.MESSAGE`, `metadata.sessionId` for deep-linking — the mobile notification-tap handler already reads `notification.sessionId`, not a chat-specific key). Best-effort, never blocks the send.

**Pagination**: `GET .../chat/messages?before=<messageId>` — cursor-based, 50 messages per page, `hasMore` in the response. Mobile's `ChatThreadView` loads the next page when the user scrolls within 200px of the top, preserving scroll position across the prepend.

**Reconnection**: the Realtime broadcast subscription is fire-and-forget by nature (a dropped connection just means missed pings), so `ChatThreadView` compensates two ways — (1) a fresh subscribe always triggers an immediate refetch (catches anything that landed in the gap before the subscription took effect, and doubles as reconnect-catchup since a `channelError`/`timedOut`/`closed` status tears down and re-subscribes a fresh channel after a 3s backoff — the underlying package throws if `subscribe()` is called twice on the same channel instance, so a genuinely new instance is required each time); (2) independently, `didChangeAppLifecycleState(resumed)` also forces a refetch, since resuming from background is exactly when a channel is most likely to have silently dropped without its error callback ever firing.

**Known gaps, not built**: typing indicators, read receipts/unread counts, presence/online status (all deliberately out of scope for this migration's v1 — the CLAUDE.md mentor-availability decision above is a real precedent for *not* building presence without a clear product reason), an admin/staff reply path for support chat (the `SUPPORT_ACCOUNT_ID` sentinel exists but nothing sends as it), and an offline send queue (a failed send surfaces a retry action, not automatic background retry). None of these block normal use; all were true of the pre-migration Stream implementation too except read receipts/typing (Stream provided those as SDK defaults but the pre-migration screens never enabled them — `disableAttachments:true`/`showCommandsButton:false` was the extent of the customization — so this is feature parity with what was actually shipped, not a regression from a richer surface).

## Local dev gotchas specific to this session

- **Flutter web caching**: `flutter build web` doesn't content-hash `main.dart.js`, so Chrome's HTTP disk cache can silently serve a stale copy after a rebuild even in a fresh tab with no service worker (confirmed via `transferSize: 0` in `performance.getEntriesByType('resource')`). Fixed two ways: (1) `mobile_flutter/scripts/no_cache_server.py` replaces plain `python -m http.server` in `.claude/launch.json`, sending `Cache-Control: no-store` and falling back unmatched paths to `index.html` (needed for go_router's path-based routing to survive a direct/deep-link load); (2) `mobile_flutter/scripts/build_web.sh` wraps `flutter build web` and appends a content-hash query string (`?v=<hash>`) to `mainJsPath` in the generated `flutter_bootstrap.js`, so every rebuild gets a guaranteed-fresh cache key. Use `build_web.sh` instead of calling `flutter build web` directly when testing web changes.
- **Backend hot-reload doesn't see new Prisma Client types**: after `npx prisma generate`, the already-running `nest start --watch` process keeps using its stale in-memory `PrismaService` types (`Property 'x' does not exist on type 'PrismaService'` for a model that very much exists) even though a fresh `tsc --noEmit` in a new shell sees it fine. Fix: stop and restart the "Backend (NestJS)" preview server (`preview_stop` + `preview_start`) after any migration, don't just wait for the watcher.
- **JWT role claims are stale after a role change**: `PATCH /users/me/role` doesn't reissue a token — the old JWT's `role` claim still says the previous role until the client calls `POST /auth/token/refresh` (which re-reads role from the DB). Relevant whenever testing a role transition (e.g. ASPIRANT → MENTOR) via curl: refresh before calling role-gated endpoints or you'll get a 403 that looks like a bug but isn't.

## Conventions to follow

- Explicit allowlist response projections (`toXResponse()` functions) for every entity — never return a raw Prisma row, to avoid leaking fields like `phoneHash`/`realNameEncrypted` as the schema evolves.
- 404 (not 403) for resources a user isn't a party to, everywhere — avoids leaking resource existence to unrelated users.
- Idempotency keys on every ledger write (`applyLedgerEntry`), derived from a stable source (hold id, report id, Razorpay payment id) — retries must never double-apply.
- Every new module gets tested against the **real** running backend + real Supabase DB (not just `tsc` passing) before being considered done — create throwaway test users/sessions via a `node -e` script with the Prisma client, `curl` the actual endpoints, verify DB state, then clean up the test data.
- **Never write "done"/"live"/"complete" — in CLAUDE.md, a commit message, or to the user — for an external action (a deploy, a dashboard/API write, a production config change) without re-reading that action's own result first.** A tool call that appears to have been issued is not the same as one confirmed to have succeeded — it can be blocked, partially applied, or silently no-op. This project has shipped at least one real instance of this: MSG91 was written up as "live in production" when the underlying Railway variable write had actually been blocked by a permission check, never re-verified before the claim was made. The fix is mechanical, not a matter of trying harder: after any external write, make one more call that reads the state back (list-variables, get-status, a fresh `curl` against the real endpoint, whatever fits) and only then write the status claim — cite what that read-back actually showed, don't infer success from the write call's own response alone.
- **For any question about live infrastructure (what host, what config, what's actually deployed) — query the live platform first, never infer it from a committed config file.** A file like `render.yaml` sitting in the repo does not mean that platform is in use; it can be stale from an earlier migration (exactly what happened — production had already moved to Railway while `render.yaml` sat untouched claiming Render). If a tool exists to ask the real platform (Railway's MCP tools in this project), use it before trusting anything committed to git about infrastructure.
- **Touch only the files a task actually requires — no incidental/exploratory edits riding along.** Before staging anything, run `git status`/`git diff --stat` and account for every file in it: either the current task's own logic required changing it, or it's a pre-existing uncommitted change from before this task that's been individually reviewed (read the diff, understand what it does) and knowingly included — never swept in just because it happened to be sitting there. A repo-wide sweep (grep-and-fix-everywhere, "clean up every mention of X") only happens when the user explicitly asked for that scope, as with the Render removal — a task scoped to "fix the OTP length bug" touches the OTP provider and its DTO, not every file that happens to mention OTP.
- **A change follows this order before it's considered done, every time:** (1) scope — name the specific files this task needs, nothing more; (2) implement; (3) compile/lint (`tsc`, `dart analyze`, whatever the language uses); (4) if it's new/changed backend behavior, live-test it against the real backend + real DB (see the module-testing rule above); (5) if it's an external write (deploy, dashboard, API), read the result back before claiming success (see the rule above); (6) re-check `git status`/`git diff` against the scope from step 1 before staging; (7) update the relevant section(s) of **this file** (CLAUDE.md) so it reflects the new reality — see the rule immediately below for why this is a real step, not an afterthought; (8) commit (code + the CLAUDE.md update together, one commit — not a separate later cleanup pass); (9) push. Skipping straight from "wrote the code" to "committed" is how an unreviewed stale file, an unconfirmed external write, or a stale CLAUDE.md claim ends up shipped.
- **Keep this file current — every session, every push, no exceptions.** CLAUDE.md is the one thing every session (and every remote/parallel worker, and every automated task runner) reads first, so it going stale is worse than it not existing: a session that trusts a stale claim here (e.g. "Firebase isn't configured," "MSG91 not yet flipped," a placeholder stream code) will waste real time re-discovering what another session already verified, or — worse — repeat work already done, or tell the user something is still pending when it's actually shipped. So: whenever a task actually lands (a real fix, a status genuinely changing from pending to done, a decision superseding an earlier one, a new admin/mobile/backend feature landing from *any* session working in this repo), update the relevant section(s) of this file in the **same commit/push** that lands the change — step 7 above, not a separate later cleanup pass that may never happen. This applies with no exceptions to every session and every remote/automated task runner working in this repo, not just interactive ones, and to work landing from concurrent sessions you didn't personally do — if you notice an undocumented merged commit while doing something else, document it on the spot rather than leaving it for whoever next needs the current picture. A stale claim caught while doing unrelated work is always worth fixing immediately (this has happened repeatedly across this project's history — OTP, Firebase, unique IDs, the mentor verification badge, the admin panel's payouts/pagination/user-detail screens, and the Discover pagination-cap + college-state-data fixes were all found undocumented mid-conversation and corrected here, sometimes by a different session than the one that shipped them), never left for someone else to re-discover.
